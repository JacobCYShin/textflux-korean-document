# 결정 기록

파라미터를 그 값으로 정한 근거와, 도중에 발견한 함정을 남긴다.
**측정 결과([findings.md](findings.md))만 보면 값의 출처를 알 수 없어 같은 실험을 반복하게 된다.**
이 문서는 그걸 막기 위한 것이다.

---

## 1. 마스크 종횡비 맞춤 — `make_field_masks.py`

### 왜 필요한가

모델은 글리프 띠의 형태와 마스크 박스의 형태를 대응시킨다.
비율이 어긋나면 박스를 채울 만큼 글자를 지어낸다. 근거는
[findings.md](findings.md#1차-요인--마스크-종횡비)에 있다.

### 종횡비를 폰트로 실측하는 이유

글자 수로 추정하지 않고 **실제 폰트로 렌더해 잉크 경계를 측정**한다.

```python
aspect = (ink_width) / (ink_height)   # probe size 120px 로 렌더 후 측정
```

한글·한자·라틴·숫자의 글자당 폭이 크게 다르기 때문이다. 같은 4글자여도
`금융기관`은 3.9:1, `金融机关`은 4.2:1, `ABCD`는 3.3:1이다.
글자 수 × 상수로 계산하면 문자 종류에 따라 최대 30% 어긋난다.

측정 캔버스는 잉크가 경계에 닿지 않을 때까지 2배씩 키운다.
긴 문자열을 고정 캔버스에서 재면 잘려서 종횡비가 과소 측정된다.

### `--slack 1.06`

계산된 폭에 **6% 여유**를 준다. 0%로 하면 글자가 박스 경계에 딱 붙어
모델이 자간을 줄이거나 글자를 눌러 넣는 경향이 관측됐다.
6%는 한 글자 폭의 1/4 미만이라 글자 수 판단을 바꾸지 않는 선에서 가장 컸던 값이다.

### `--align left`

기입란은 왼쪽부터 채우는 것이 자연스럽고, 실제 서식의 필드도 좌측 정렬이다.
`center`/`right`도 지원하지만 측정에는 사용하지 않았다.

### 폭이 필드보다 커지는 경우

문자열이 인쇄된 칸보다 길면 **칸 전체 폭으로 고정(clamp)하고 로그에 `CLAMPED`를 남긴다.**
칸을 넘겨 그리면 마스크가 괘선을 덮어 서식이 훼손된다.
`USD 1,250,000.00`(8.4:1 필요, 8.8:1 가용)과 `110-234-567890`(9.4:1 필요)이 여기 해당한다.

## 2. 크롭·확대 — `make_crop_inputs.py`

### 왜 필요한가

종횡비를 맞춰도 짧은 단어가 계속 틀렸다.
텍스트 줄 81px은 잠재 공간에서 세로 5행이고, `ㅣ`와 `ㅓ`를 가르는 획이 2 × 0.5 패치에 불과하다.
근거는 [findings.md](findings.md#2차-요인--잠재-공간-해상도)에 있다.

### `--target-line-height` 192 → 288

| 시도 | 줄 높이 | 잠재 세로 | 결과 |
| --- | --- | --- | --- |
| 교정 없음 | 81 px | 5행 | `가나다` 완전 실패 |
| 1차 (192 지정) | 197 px | 12행 | **`금융기관` 최초 2/3 완전 일치** |
| 2차 (288 지정, 문맥 손실) | 291 px | 18행 | `신` 최초 정확 1건, 그러나 스타일 붕괴 |
| 3차 (288 지정, 문맥 유지) | 259 px | 16행 | 겹받침 3/3, `ABCD` 3/3 |

지정값과 실제값이 다른 이유는 32배수 정렬과 MP 상한 때문이다(아래 참조).

### `--context-x 4.5` ← **가장 중요한 값**

필드 높이의 배수로 지정한다. 4.5가 나온 근거는 데모 서식지의 실측이다.

```
항목명 '성명'의 잉크 범위 : x = 78 ~ 221
기입란 시작              : x = 420
필드 높이                : 81 px

context-x 3.0 → 크롭 시작 x = 420 - 243 = 177   → 라벨 잘림
context-x 4.5 → 크롭 시작 x = 420 - 364 =  56   → 라벨 포함
```

**라벨이 잘리면 스타일이 붕괴한다.** TextFlux는 스타일 인코더가 없어
마스크 밖의 인쇄 텍스트에서 글자체를 유추하는데, 크롭에 인쇄 글자가 하나도 없으면
참고할 대상이 사라진다. 2차 시도에서 빨간 글씨·볼드체·엠보싱·글자 중복이 나타난 원인이 이것이다.

> **다른 서식으로 옮길 때는 이 값을 다시 계산해야 한다.**
> 필드 높이와 라벨까지의 거리 비율이 다르면 4.5가 맞지 않는다.
> `--dry-run`으로 크롭 폭을 먼저 확인하는 것이 안전하다.

### `--context-y 0.5`

1차에서는 1.2였다. 288px 목표를 유지하면서 `--context-x 4.5`를 되찾으려면
캔버스 예산이 부족해 세로를 깎았다.

**항목명이 필드와 같은 행에 가로로 놓여 있으므로 세로 문맥을 줄여도 라벨은 살아남는다.**
0.5(약 40px)면 기입란 테두리와 위아래 괘선이 크롭에 들어간다.

| `--context-y` | 줄 높이 | 잠재 세로 | 캔버스 MP |
| --- | --- | --- | --- |
| 1.2 | 208 px | 13.0 | 2.37 |
| 0.8 | 234 px | 14.6 | 2.41 |
| **0.5** | **259 px** | **16.2** | **2.46** |
| 0.35 | 247 px | 15.4 | 2.21 |

0.35에서 오히려 줄어드는 것은 32배수 정렬이 다른 값으로 떨어지기 때문이다.

### `--max-megapixels 2.6`

캔버스(글리프 띠 + 이미지)가 이 값을 넘으면 배율을 0.92배씩 낮춘다.

2.6을 고른 이유는 **관측된 안정 구간의 상한**이다.

| 캔버스 | 관측 |
| --- | --- |
| 0.85 ~ 2.6 MP | 스타일 안정 |
| 3.0 ~ 3.7 MP | 글자 중복(`선선청서`), 색상 이상, 엠보싱 |

교정 전 전체 이미지 실행도 2.54 MP였고 스타일은 안정적이었다(내용만 틀렸다).
FLUX 계열이 학습 해상도를 크게 넘기면 반복 아티팩트를 내는 알려진 성질과 일치한다.

### `--min-canvas-width 1024`

좁은 필드(예: 2글자)는 크롭이 작아져 캔버스가 0.4 MP 수준까지 떨어진다.
너무 작으면 글리프 띠 높이(폭 × 0.15625)도 같이 작아져 조건 그림의 해상도가 무너진다.
확대 후 폭이 1024px에 못 미치면 크롭을 좌우로 넓혀 채운다.

### 32배수 캔버스 정렬

업스트림 `run_inference()`가 합성 캔버스를 **32의 배수로 내림 반올림**한다.

```python
new_width  = (w // 32) * 32
new_height = (h // 32) * 32
```

미리 맞춰두지 않으면 여기서 재샘플링이 한 번 더 일어나 글자가 미세하게 눌린다.
글리프 충실도를 측정하는 작업에서 불필요한 변형이므로 반올림이 no-op이 되도록 계산한다.

```python
width  = round(crop_w * scale / 32) * 32
strip  = int(width * 0.15625)                 # 띠 높이는 폭으로 결정됨
height = ceil((strip + target_h) / 32) * 32 - strip   # (strip + height) 가 32의 배수
```

세로는 띠 높이를 뺀 값으로 정해야 하므로 계산이 한 단계 더 들어간다.
검증에서 전 케이스 `W % 32 == 0` 및 `(strip + H) % 32 == 0`을 확인했다.

### 마스크 리사이즈는 `NEAREST` + 재이진화

`LANCZOS`나 `BILINEAR`로 줄이면 경계에 회색 픽셀이 생긴다.
`validate_cases.py`는 0/255가 아닌 픽셀이 1%를 넘으면 거부한다.

```python
crop_mask  = mask.resize((w, h), Image.NEAREST)
mask_array = np.where(np.array(crop_mask) >= 128, 255, 0).astype(np.uint8)
```

`NEAREST`만으로도 대체로 이진이 유지되지만, 임계값을 한 번 더 적용해 보장한다.

### 되붙이기 검증

`paste_crop_results.py`가 결과를 원본 크기로 축소해 원위치에 붙인다.
**크롭 박스 밖 영역이 원본과 바이트 단위로 동일함**을 15케이스 전부에서 확인했다.
크롭 안쪽의 평균 절대 오차는 255 단계에서 1.6~3.7이며, 이는 확대·축소 왕복 손실이다.

반환 이미지 높이가 입력과 몇 px 다를 수 있으므로(6단계 비율 크롭 때문),
마스크 좌표는 크기 비율로 보정한다.

## 3. 실행 구조 — `run_suite.py` 대 `run_resident.py`

### `run_suite.py`의 한계

케이스마다 컨테이너를 새로 만들고 지운다. 두 가지 문제가 있다.

1. **모델을 케이스마다 다시 로드한다.** 페이지 캐시가 따뜻하면 로드가 1초 미만이라
   실측 영향은 작았지만(케이스당 총 32초 중 추론 18초), 구조적으로 낭비다.
2. **재개가 안 된다.** 기존 run 디렉터리를 만나면 `refusing to overwrite existing run`으로
   **전체 실행을 중단**한다. 절반쯤 진행된 상태에서 다시 돌리면 이어서 하지 못한다.

2번이 실제로 문제가 됐다. 45회 중 10회에서 중단된 뒤 재실행하면
`run_sweep.sh`가 결과 디렉터리 존재를 보고 그 단계를 통째로 건너뛰어 영구 미완으로 남았다.

### `run_resident.py`로 전환

한 프로세스에서 파이프라인을 한 번만 올리고 매니페스트를 순회한다.

| | `run_suite.py` | `run_resident.py` |
| --- | --- | --- |
| 모델 로드 | 케이스마다 | 샤드당 1회 |
| 재개 단위 | 없음 (전체 중단) | **케이스 단위** |
| GPU | 1장 | N장 병렬 |
| 실행 위치 | 컨테이너 밖 (컨테이너를 생성) | 컨테이너 안 |

케이스 단위 재개는 검증했다 — 45건 중 임의의 7건을 지우고 재실행하니
샤드들이 정확히 그 7건만 만들고 나머지는 건너뛰었다.

**두 러너의 결과를 한 표에 섞지 않는다.** `case.json`의 `provenance` 필드로 구분된다
(`run_suite.py`는 격리 실행을 강제하고 기록하며, `run_resident.py`는 `interactive-resident`로 남긴다).

### `--shard-by case`가 기본인 이유

실행 단위로 자르면(`--shard-by run`) 같은 케이스의 시드 42/43/44가 서로 다른 GPU로 흩어진다.
**재현성을 측정하는 실험에서 시드 차이와 GPU 차이가 섞여 해석이 불가능해진다.**

케이스 단위로 자르면 한 케이스의 모든 시드가 한 GPU에 머문다.
부하 균형은 조금 손해다(9케이스가 4샤드에서 9/6/6/6으로 갈린다).

### 샤드 스태거 20초

샤드를 동시에 띄우면 여러 프로세스가 같은 가중치 파일을 동시에 읽어 첫 로드가 크게 느려진다.
20초 간격으로 계단식 시작한다. `STAGGER=0`으로 끌 수 있다.

### 샤드별 작업 디렉터리

업스트림이 `resource/font/...`와 `outputs_my/`를 **작업 디렉터리 기준 상대 경로**로 쓴다.
같은 컨테이너에서 여러 프로세스를 띄우면 `outputs_my`를 공유해 서로 덮어쓴다.

`get_next_seq_number()`가 디렉터리를 스캔해 빈 번호를 찾는 방식이라
동시 실행 시 같은 번호를 잡는다. **에러 없이 결과가 섞인다.**

샤드마다 개인 작업 디렉터리를 만들어 해결한다.

```
/tmp/textflux-workspaces/<suite>/shard-00/
    resource   -> /opt/textflux/app/resource   (심링크)
    outputs_my -> <해당 케이스의 run 디렉터리>   (케이스마다 갈아끼움)
```

4샤드 동시 출력이 완전히 격리됨을 확인했다.

## 4. 시드를 3개 쓰는 이유

1개로는 계통적 결함과 샘플링 잡음을 구분할 수 없다.

실제로 판단이 갈린 사례가 있다. `금융기관`이 종횡비 교정 직후 1시드에서 3/4자 정확으로 나와
"거의 되는 상태"로 보였으나, 3시드로 늘리자 `기→지` 2건, `기→가` 1건으로
**단 한 번도 완전 일치가 없었다.**

반대로 `신`은 3시드에서 3회 모두 동일하게 실패해 **결정론적 결함**으로 확정됐고,
그래서 "시드를 더 늘려도 해결되지 않는다"는 결론을 낼 수 있었다.

3개는 1/3과 2/3과 3/3을 구분할 수 있는 최소 개수다.
파라미터 스윕에서는 2개로 줄여 실행 수를 절약했다.

## 5. 도중에 발견한 함정

### 상대 경로 두 개가 만든 문제

```python
# run_inference.py:169  (단일 행 경로)
font = ImageFont.truetype("resource/font/Arial-Unicode-Regular.ttf", 60)
# run_inference.py:349  (다중 행 경로)
base_font = ImageFont.truetype("resource/font/Arial-Unicode-Regular.ttf", 40)
# run_inference.py:390, 472~489
result_path = os.path.join("outputs_my", f"result_{seq_str}.png")
```

**한글이 깨지던 원인은 폰트 파일이 아니라 실행 위치였다.**
한글 폰트를 올바르게 넣었는데도 증상이 그대로였고, 작업 디렉터리가 달라
폰트를 못 찾고 `except IOError`로 기본 폰트로 조용히 넘어가고 있었다.

**오류가 나지 않는다.** 경고 한 줄만 남고 정상 종료되며 한글만 네모 상자로 나온다.
이 때문에 진단이 하루 늦어졌다.

대응:
- 실행 시 작업 디렉터리를 `/opt/textflux/app`으로 고정
- `run_resident.py`가 시작 시 폰트를 검사한다. `금`과 `융`을 렌더해
  **둘이 픽셀 단위로 동일하면 .notdef 상자로 판단하고 즉시 실패**시킨다.
  파일 존재 확인만으로는 잡히지 않는다

### `validate_cases.py`의 존재하지 않는 API

```python
values = grayscale.get_flattened_data()   # Pillow에 없는 메서드
```

`AttributeError`가 `main()`의 `except (OSError, ValueError)`에 걸리지 않아 트레이스백으로 죽었다.
**마스크 검증이 한 번도 성공한 적이 없었다.** `getdata()`로 수정했다.

교훈: 검증 스크립트도 검증해야 한다. `tests/test_scripts.py`가 이 경로를 덮는다.

### `--guidance-scale`이 전달되지 않았다

`offline_infer.py`는 인자를 받는데 `run_suite.py`가 넘기지 않아 **기본값 30.0에 고정**돼 있었다.
스윕 이전의 모든 측정이 검증되지 않은 값으로 수행된 것이다.

`run_suite.py`에 인자를 추가하고 `case.json`에 `steps`·`guidance_scale`을 기록하도록 했다.
서로 다른 설정의 결과가 섞이는 것을 막기 위한 것이다.

### 변수를 두 개 이상 동시에 바꾼 실패

2차 크롭 실험에서 해상도를 올리면서 **캔버스 예산을 맞추려 `--context-x`를 4.5에서 3.0으로 줄였다.**
결과가 나빠졌으나 원인을 해상도 탓으로 돌릴 수 없었다 — 문맥과 캔버스 크기도 함께 바뀌었기 때문이다.

3차에서는 세로 문맥만 조정해 **가로 문맥과 캔버스 크기를 1차와 같게 유지**하고 해상도만 올렸다.
파라미터 스윕도 같은 원칙으로 설계했다 — 모든 단계가 동일한 크롭 입력을 쓰고
`crop-probe-v3`를 기준선으로 삼아 한 번에 한 값만 바꾼다.

### 조건이 목적과 무관한 상태로 판단하려 한 것

초기 실행은 업스트림 예제인 **중국어 서예 간판**을 사용했다.
결과가 나빴으나 이는 "중국어 간판을 한글로 바꾸지 못한다"는 정보였을 뿐,
흰 종이 위 인쇄 서식 성능과는 무관했다.

**"실행 환경이 도는가"와 "모델이 목적 조건에서 잘하는가"를 분리**한 뒤에야
의미 있는 측정이 시작됐다. 전자를 완료한 시점에 후자는 시작도 하지 않은 상태였다.

### 반복 삽입은 캔버스 크기와 상관된다

`2026. 08. 08. 28.`, `SHBKKKRSE`, `선선청서` 같은 구간·글자 반복이
캔버스 3.0 MP 이상에서 집중적으로 나타났다.
확산 모델이 학습 해상도를 크게 넘길 때 나오는 알려진 결함과 일치한다.

숫자 필드는 마스크가 넓어 크롭 후 7.6:1의 극단적 가로형 캔버스가 되며,
이것이 숫자 필드 역행의 유력 가설이다. **아직 측정하지 않았다.**

## 6. 코드를 읽을 때 볼 곳

업스트림 `run_inference.py`에서 동작을 결정하는 지점만 추린다.

| 함수 | 무엇을 결정하는가 |
| --- | --- |
| `process_normal_mode()` | `--words` 줄 수로 단일 행/다중 행 분기 |
| `render_single_line_text()` | 띠 높이 = 원본 **폭** × 0.15625 |
| `draw_glyph_flexible()` | 글자 자동 확대, `max_font_size` 140 (폭 > 1280이면 200) |
| `process_singleline_mode()` | 세로 결합, 띠 마스크는 완전 검은색 |
| `run_inference()` | 32배수 내림 반올림, `prompt`(CLIP)와 `prompt_2`(T5) 분리 |
| `generate_prompt()` | 문구가 들어가는 프롬프트 템플릿 |
| `save_results()` | `outputs_my/` 하위 산출물 저장 (상대 경로) |

**`draw_glyph2()`와 `render_glyph_multi()`는 다중 행 경로 전용이다.**
자간 자동 삽입과 회전 처리가 들어가 단일 행과 동작이 다르므로,
단일 행 측정 결과를 다중 행에 적용해서는 안 된다.
